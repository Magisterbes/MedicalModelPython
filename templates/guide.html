📖 Data format & getting started

← Back to the model

1. What the model needs

The simulation is driven by two CSV datasets:

  • Aggregate incidence & mortality data — age-specific population, cancer cases and deaths. Used to build the initial age distribution and the natural mortality, and to fit the diagnosis and cancer-death hazards.
  • Individual staging data — one row per diagnosed patient (age, stage, aggressiveness). Used to train the stage-by-age model and the Gompertz tumour-growth models.

The repository ships with several ready-made datasets, so you can run the model immediately without uploading anything. Pick one in the Dataset box of the parameter panel: the selector sets the aggregate and the staging file together, so the two can never end up coming from different populations. See Appendix A for the full list, its provenance and citation, and for how to add your own.

Advanced. Under Advanced: choose files individually you can still point the aggregate and staging inputs at any validated CSV in data/, including files you uploaded yourself.
Delimiter. Both files are semicolon-separated (;), not comma-separated, and must contain a header row with the exact column names below.

Default name: data_agg_rus.csv. One row per single year of age.

Requirements: at least one row for every age you care about (0–110 is expected). Column names are matched exactly, including spaces.

3. Staging file format

Default name: data_ind.csv. One row per diagnosed patient.

ColumnTypeRangeMeaning

Age;Stage;Aggressiveness
70;4;1
47;4;1

...

All four stages and both aggressiveness values should be present, otherwise the fitted models are extrapolating from a narrow sample.

4. From scratch: upload → fit → simulate

  1. Prepare the two CSV files as described above, with exact header names.
  2. Open the app and expand ⚙ Parameters.
  3. Upload. In the Upload CSV box choose the file, pick Aggr or Stage next to it, and click Upload. The status line reports the validation result (row count, or the exact problem).
  4. Select. Pick a shipped dataset in the Dataset box, or expand Advanced: choose files individually to point Aggregate data and Staging data at your own files. Leaving both at (default from config) keeps the built-in pair from config/parameters.toml.
  5. Set the run size. Population, Years and (optionally) Seed. Budget roughly 1.3 KB of RAM per agent at peak: a million agents needs about 1.3 GB.
  6. Run. 🔧 Fit + Simulate calibrates the parameters on your data and then simulates; ▶ Run Only simulates with the current parameters. Charts and summary cards appear below once the progress bar completes.
  7. Export (optional). 💾 Save / 📂 Load store and restore the parameter set as JSON.
  8. Sensitivity (optional). 📊 Sensitivity re-runs the model for a range of lead-time multipliers and plots how the results move.
Fastest sanity check. Upload both files → select them → ▶ Run Only with a small population (e.g. 20 000). If that works, run 🔧 Fit + Simulate.

5. Downloads: agent history and chart CSVs

After every Fit + Simulate or Sensitivity run a ⬇ Downloads panel appears listing the generated files. They are written to disk once, in chunks, and served from there — nothing large is held in memory.

Single run

  • agents.csv — one row per agent, including healthy ones (age, death cause, cancer onset, stage ages, treatment, screening, …).
  • agents_cancer.csv — the same columns, cancer patients only.
  • chart_incidence.csv, chart_mortality.csv, chart_stages.csv, chart_survival.csv, chart_years_saved.csv, chart_diagnosis_rates.csv — the data behind each chart on the page.
  • summary.csv — the summary metrics, one per row.
  • meta.json — run metadata and a legend for every agent column.

Sensitivity

  • sens_chart_*.csv — one file per chart; the first column is the x axis, then one column per lead-time factor.
  • sens_metrics.csv — aggregate metrics for every factor.
  • agents_factor_<x>.csv — per-agent history for that factor (cancer patients only, to keep the size down).

Each run writes into its own directory (output/exports/<run_id>/) and the download links carry that id: a link is only valid for the run that produced it, so /api/download/<run_id>/<file> with somebody else's id returns 404.

Only the newest runs are kept — starting a new run prunes older bundles (EXPORT_DIRS_KEPT, 3 by default). On a hosted instance the folder is also lost when the service restarts, so download what you need before then. Data files use ; as the delimiter, like the input files.

6. Uploading over the API (optional)

curl -X POST -F "file=@my_aggregate.csv" -F "type=aggregate" http://localhost:5000/api/data/upload
curl -X POST -F "file=@my_staging.csv"   -F "type=staging"   http://localhost:5000/api/data/upload

A successful upload returns {"status":"ok","filename":"...","validation":"OK (N rows)"}. Invalid files are rejected with a message and are not stored. Then run with the uploaded files selected:

curl -X POST http://localhost:5000/api/simulate \
     -H "Content-Type: application/json" \
     -d '{"population":20000,"seed":42,"fit":true,
          "override_params":{"train_data_filename":"my_aggregate.csv",
                             "train_staging_data_filename":"my_staging.csv"}}'

To see what the Dataset dropdown offers, and where each file came from:

curl http://localhost:5000/api/datasets        # named datasets + provenance
curl http://localhost:5000/api/data/list       # every validated CSV, classified

7. Uploads in Docker

Uploading works in the Docker image: the container runs as a non-root user, but /app/data is writable, so the file is validated and stored there.

The container filesystem is ephemeral. An uploaded file is lost when the container is recreated — a redeploy, or any restart that starts a fresh container. docker-compose.yml mounts data/ on the host, so under Compose the file survives; the datasets committed to the repository always survive either way.

A file is stored under its sanitised name; uploading the same name again replaces it. Files that belong to a shipped dataset cannot be overwritten. The file only affects a run when it is selected in the Advanced dropdowns.

9. Two people using the site at once

One instance runs one simulation at a time — a second population would need about as much memory again — so the app serialises the work and keeps each visitor's results apart instead:

  • One run at a time. If a simulation is already running, a new request is refused with 409 and “Another simulation is already running on this instance”. Wait for it to finish and try again. The busy flag is taken atomically, so two requests arriving in the same instant cannot both start a run.
  • Every run has an id. A run returns its run_id; the page keeps it in the browser tab (sessionStorage) and ignores any status, chart or download carrying a different one. You are never shown another visitor's results — if someone else's run finishes while your page is open, the status line tells you so instead.
  • Downloads belong to their run. Each run writes to its own directory and its links are /api/download/<run_id>/<file>. A link from another run (or the old link without an id) returns 404.
  • Reloading is safe. Reload the page during your own run and it resumes watching it; another visitor's run is never adopted.
What is still shared. Uploaded CSVs live in a single data/ folder, so two people uploading the same file name overwrite each other and every uploaded file is visible to everyone. Files that belong to a shipped dataset (Appendix A) cannot be overwritten by an upload at all, and a rejected upload never deletes an existing file. Ask before re-using a file name, and download your results while they are still on disk.

Appendix A: the shipped datasets

The datasets offered in the Dataset box are listed in data/datasets.json. Choosing one sets the aggregate data file and the staging data file together, so a mismatched pair (a United States aggregate with German staging, say) cannot be picked by accident. An entry whose CSV is missing from data/ is dropped automatically, and the interface shows the description, the totals and the citation stored next to the files.

Colorectal · USA

Both sexes, United States of America. The aggregate file holds 151 162 new cases and 52 924 deaths on a population of 334 805 268 — a crude incidence rate of 45.15 per 100 000, matching the published GLOBOCAN rates (colon 31.43 + rectum 13.72).

Colorectal · Germany

Both sexes, Germany. Same pipeline, but a markedly older population: 59 851 new cases and 25 844 deaths on 83 883 587 people — 71.35 per 100 000, about 1.6× the American crude incidence. On an otherwise identical run (20 000 agents, 30 years, same seed) it produces noticeably more colorectal cases than the US dataset, which is a quick way to check that a run really used the data you selected.

Citation. Ferlay J, Ervik M, Lam F, Laversanne M, Colombet M, Mery L, Piñeros M, Znaor A, Soerjomataram I, Bray F (2024). Global Cancer Observatory: Cancer Today (version 1.1). Lyon, France: International Agency for Research on Cancer. https://gco.iarc.who.int/today
The staging file is synthetic. GLOBOCAN publishes incidence and mortality only. The stage and aggressiveness records are drawn from the real incidence-by-age profile using a literature-based stage mix; they demonstrate the workflow and must not be read as registry data.

All-cause mortality (deaths all), which GLOBOCAN does not publish either, is a Makeham–Gompertz pattern calibrated to the country's life expectancy (77.5 years for the USA, 80.7 for Germany); the model only uses its shape.

Regenerating a dataset, or adding your own country

Both GLOBOCAN datasets are committed to the repository, so the app never calls the API at runtime. To rebuild them, or to build a third country, pass the country to the two tools:

python tools/build_globocan_dataset.py --country 840 --country-name "United States of America" \
       --out-prefix globocan_colorectum_usa --life-expectancy 77.5
python tools/build_globocan_dataset.py --country 276 --country-name Germany \
       --out-prefix globocan_colorectum_germany --life-expectancy 80.7
python tools/make_synthetic_staging.py --prefix globocan_colorectum_germany

Country codes are ISO numeric (840 USA, 276 Germany, 392 Japan, …); the scripts query the GLOBOCAN 2022 gateway at gco-api.iarc.fr. Then add one entry to data/datasets.json and restart:

{
  "id": "globocan2022_colorectum_japan",
  "label": "GLOBOCAN 2022 · Colorectal · Japan",
  "aggregate": "globocan_colorectum_japan_agg.csv",
  "staging": "globocan_colorectum_japan_ind.csv",
  "default": false,
  "synthetic_staging": true,
  "description": "Colorectal cancer, both sexes, Japan.",
  "source": "GLOBOCAN 2022 (version 1.1), IARC",
  "citation": "Ferlay J, et al. (2024). Global Cancer Observatory: Cancer Today (v1.1)."
}

That is the whole procedure: the file names in the entry are all the application needs, so no code changes are involved. default: true may appear on at most one entry; synthetic_staging: true controls the warning tag shown next to the dataset in the interface.

Appendix B: Gompertz model parameters

Tumour growth follows the reduced Gompertz model:

V(t) = exp(K - exp(C - B * t))      B = exp(log(B_pop) + eps),  eps ~ N(0, B_std^2)

where V(t) is tumour size (a proxy for stage) at time t since cancer onset. The aggressive and non-aggressive groups have separate parameter sets; all four values can be edited individually in the parameter panel.

ParameterMeaning
K Carrying capacity. V(t) approaches exp(K) as time grows, so a larger K means a larger final tumour.
C Shape / offset parameter. Sets the initial size V(0) = exp(K − exp(C)), which is close to 0, and places the inflection point of the curve at t = C / B.
B_pop Population-mean growth rate, on a log scale. Larger values mean faster progression; each patient draws B = exp(log(B_pop) + eps).
B_std Standard deviation of the individual random effect on log(B) in the model definition. It is stored and passed through faithfully, but the current simulation engine takes each agent's growth rate from Growth rate limits and the aggressiveness threshold, so changing B_std does not alter simulated results yet.

MedicalModel2024 — academic use. Based on Magisterbes/BespalovPhd.
